## 草稿一：deepseek-harness 宿主缺陷（app-boot 模块解析崩溃）

- 上游仓库：https://github.com/deepseek-ai/deepseek-harness
- 语言习惯：英文正文 + 中文备注
- 提交入口：https://github.com/deepseek-ai/deepseek-harness/issues/new

### 建议标题

```
[app-boot] TypeError: createRequire.resolve.paths is not iterable — legacy packages without `exports` (e.g. mongodb@7.6.0) crash Module._resolveFilename and break plugin loading
```

### 正文（可整段复制提交）

**Environment**

- OS: Windows 11
- Node.js: v24.19.0
- dsh: 0.1.7-rc.1 and 0.1.7-rc.2 (both affected)

**Summary**

Plugin loading fails with `failed to import` and no actionable error whenever a plugin dependency uses a legacy package layout without an `exports` field. Root cause is an unguarded call to `require.resolve.paths()` inside `ResolutionRouter.routeScoped`, which returns `null` for core-module requests per the [official Node.js docs](https://nodejs.org/api/modules.html).

**Crash location**

`@deepseek-ai/dsh-app-boot/lib/index.js` line 1422 (`ResolutionRouter.routeScoped`):

```js
for (const searchPath of createRequire(parent).resolve.paths(name)) {
```

`require.resolve.paths(request)` returns **null** for:

- core modules (`fs`, `node:fs`, …)
- requests beginning with `/`, `./`, or `../`

This line has no null guard, so a core-module request flowing through the rewritten `Module._resolveFilename` throws:

```
TypeError: createRequire.resolve.paths is not a function or its return value is not iterable
    at ResolutionRouter.routeScoped (.../dsh-app-boot/lib/index.js:1422:58)
    at ResolutionRouter.routePath (...:1554)
    at Module.wrappedFilename [as _resolveFilename] (...:1771)
```

Note: the sibling call in the same project (`profile.ts:596`) already guards with `?? []` — this line was missed.

**Trigger surface**

- `mongodb@7.6.0` ships a legacy layout with no `exports` field (132 js files). All of its internal requests route through the rewritten `Module._resolveFilename`; the first core-module request crashes.
- Packages that declare `exports` (e.g. `bson@7.3.3`) do **not** trigger the bug, because modern resolution bypasses this path.
- Impact: any plugin depending on `mongodb` (in our case `dsh-db-tool`) fails to load (`failed to import`), and MongoDB connectivity is completely unavailable.

**Suggested fix**

```js
for (const searchPath of createRequire(parent).resolve.paths(name) ?? []) {
```

We also audited the unmodified rc.2 sources and found **3 more unguarded `resolve.paths()` calls** (bundled `lib/index.js`, approximately lines 1482, 2026, 3270) — recommend hardening all of them in one pass.

**Additional observations (same area, lower severity)**

1. `selfReferenceName()` short-circuits self-reference resolution only for packages that declare an `exports` field. Legacy packages without `exports` fall through to the full routing path; consider adding a fallback for them.
2. The plugin startup audit only reports `failed to import` (originating from app-boot's `inactiveEntries`), swallowing the original error and stack trace. We could only localize this bug with a "shadow entry bisection" technique (7 probe entries on the same profile, each importing a submodule one by one). Please consider surfacing the original error and adding a debug flag.

> **中文摘要**：`dsh-app-boot` 第 1422 行对 `require.resolve.paths()` 的返回值无空值保护，core 模块请求直接抛 TypeError；无 `exports` 的老式包（mongodb@7.6.0）内部请求全部流经被改写的 `Module._resolveFilename`，导致依赖它的插件（dsh-db-tool）加载失败且 MongoDB 功能不可用。建议修复为 `resolve.paths(name) ?? []`，并加固同类另外 3 处无保护调用（bundled `lib/index.js` 约 L1482/L2026/L3270）。附带两个观察：`selfReferenceName()` 对无 `exports` 包缺少降级处理；插件审计日志吞掉原始错误与堆栈，建议输出原始错误并加调试开关。

## 草稿二：@xxxyz/dsh-mcp-manager 配置覆写缺陷（按块误删条目）

- 包：`@xxxyz/dsh-mcp-manager@2.2.7`
- 语言习惯：中文正文
- 提交入口：https://github.com/xxxyz/dsh-mcp-manager/issues/new

### 建议标题

```
配置编辑/删除按「块」而非「条目」粒度处理，同一 `- insert:` 块内的无标记条目被连带删除
```

### 正文（可整段复制提交）

**环境**

- 包版本：`@xxxyz/dsh-mcp-manager@2.2.7`
- 平台：Windows 11 · Node v24.19.0 · dsh 0.1.7-rc.2

**摘要**

插件通过 patch 文件向宿主配置追加 `- insert:` 块。经阅读 `lib/index.js` 确认根因：**所有定位与删除操作都以「块」为单位，而不是以「条目」为单位**。同一块内由用户手工添加的、未被插件标记的条目，会在一次编辑或删除操作中被连带删除。

**根因（源码定位，`lib/index.js`）**

| 位置 | 函数 | 行为 |
|---|---|---|
| 678–691 行 | `insertBlockRange()` | 匹配到目标 id 后，返回从 `- insert:` 行到下一个顶层 `- ` 行的**整块**范围 |
| 713–721 行 | `removeEntryAll()` | 将 `insertBlockRange()` 返回的**整块**并入删除集 |
| 1074–1079 行 | UI「编辑」 | 先删整块再重写 |
| 1160–1163 行 | UI「删除」 | 先删整块 |
| 657–677 行 | `markerRanges()` | 插件自身标记的范围同样按整块计算 |

**实际事故还原**

- 事故场景：4 条 MCP 配置位于同一个 `- insert:` 块内，用户在 UI 中编辑/删除其中 1 条，结果 4 条全部丢失。
- 文件证据：`cordis.patch.yml` 从 82 行被改写为 49 行，最终仅剩 1/4 条 MCP。
- 免疫尝试失败：给手工条目补上 `# dsh-mcp-manager:server:<id>` 标记注释也**不能**避免连带删除——`markerRanges()`（657–677 行）按整块计算标记范围，块内任何操作仍波及全部条目。

**建议修复**

按「条目」粒度定位（解析条目缩进层级，定位单条 `- name:` 起始范围）替代整块删除；若短期内不便重构，至少在文档与 UI 中明确警示「同一 `- insert:` 块内的多条配置会被一起删除」。

> **中文摘要**：`insertBlockRange()` / `removeEntryAll()` / UI 编辑与删除均按整块处理，同块内无标记（或甚至有标记，`markerRanges()` 同样按块计算）的条目被连带删除，曾导致 4 条 MCP 配置一次操作全丢（cordis.patch.yml 82 行 → 49 行）。建议改为条目级定位删除，或在文档/UI 明确警示。
