## 一、问题 1 根因官方定论（dsh-db-tool 加载失败）

### 官方语义依据

Node.js 官方文档（[Modules: CommonJS modules — require.resolve.paths(request)](https://nodejs.org/api/modules.html)）明确规定：

> `require.resolve.paths(request)`
> Returns:
> - `<string[]> | null`
>
> Returns an array containing the paths searched during resolution of `request` or **`null` if the `request` string references a core module, for example `fs` or `node:fs`**, or **if the request is a relative or absolute path identifier**（即以 `/`、`./`、`../` 开头的请求）.

即：**当 request 引用 core module（`fs`、`node:fs` 等）或以 `/`、`./`、`../` 开头的路径时，`resolve.paths` 必然返回 `null`**——这不是边界情况，而是文档写明的正常返回值。

### 缺陷位置

原记录所指缺陷形态（无空值保护的 `resolve.paths` 迭代）在 `@deepseek-ai/dsh-app-boot/lib/index.js` 中有多处。**0.1.7-rc.2 实测现状**：

```js
// 原始缺陷形态（无保护，for..of 对 null 迭代即抛 TypeError）：
for (const searchPath of createRequire(parent).resolve.paths(name)) {
```

- `L1422-1429`（`routeScoped` 内）：**已于 2026-09-25 被打入一份 local hotfix**（fallback 到 `_nodeModulePaths`），语义上已挡住该路径的崩溃，原堆栈中的 `1422:58` 即修复前的这里；
- **`L1247`（`nativePackageDir`）：与上述缺陷形态逐字相同、无保护，即本次修复对象**；
- 另有 `L1482`、`L2026`、`L3270` 三处同类无保护调用（属同类隐患，归上游 issue 一并加固，本次不动）。

该形态**无空值保护**（对比同项目 `profile.ts:596` 的同类调用带 `?? []` 兜底）。凡 core module 或相对/绝对路径请求流经此处，对 `null` 做 `for...of` 迭代即抛出。

### 原错误堆栈（摘自原记录文档）

```
TypeError: createRequire.resolve.paths is not a function or its return value is not iterable
    at ResolutionRouter.routeScoped (.../dsh-app-boot/lib/index.js:1422:58)
    at ResolutionRouter.routePath (...:1554)
    at Module.wrappedFilename [as _resolveFilename] (...:1771)
```

### 触发链（四层因果摘要）

1. dsh 为实现 profile 感知解析，改写 CJS 的 `Module._resolveFilename`，**每个模块请求**都流经被改写解析路径上的 `resolve.paths` 调用（含本次缺陷行 `L1247`）；
2. `mongodb@7.6.0` 为**无 `exports` 字段的老式布局**（132 个 js 文件），`selfReferenceName()` 不短路，内部请求全部进入缺陷路径；请求 core module（如 `fs`）时 `resolve.paths` 返回 `null` → 崩溃（`bson@7.3.3` 有 exports，不触发）；
3. db-tool 的加载链 `dist/guard/index.js:10` 对 mongodb 适配器做了静态导入，**加载插件必然加载 mongodb**；
4. dsh 启动审计吞掉原始异常，只打印 `failed to import`，无堆栈线索。

### ② 插件侧 patch：保持不变

- `patches/dsh-db-tool@0.1.8.patch`（3454 字节）：将 `DANGEROUS_OPS` / `READ_OPS` 两个纯数据集合拆入 `dist/adapters/mongodb/ops.js`，使 `guard/index.js` 的静态导入不再牵连 mongodb → 插件激活不再踩中宿主缺陷。

## 四、pnpm patch 官方升级流程

引用：[pnpm 官方文档 — pnpm patch](https://pnpm.io/cli/patch)。当被 patch 的包需要升级版本时，按以下顺序操作（以 billion-context 从 0.1.147 → 0.1.163、dsh-db-tool 升级为例）：

1. `pnpm patch <pkg>@<新版本>` —— 按新版本重新生成可编辑副本，在新副本上重做补丁修改（新版 dist 若为压缩格式，旧 patch 上下文无法落位，**必须重新生成**）；
2. 用 `--patch-dir` 输出的目录内容生成/复制新 patch 文件到 `patches/`；
3. 修改 `pnpm-workspace.yaml` 的 `patchedDependencies`，将声明指向新版本；
4. **紧接**执行 `pnpm add <pkg>@<新版本>` —— 切换 patch 声明与升级之间**不插入任何其他 pnpm 命令**，否则旧版本退出依赖树的瞬间 patch 声明失配，触发 `ERR_PNPM_UNUSED_PATCH` 直接拒绝整个操作。

> 本机实证见原记录文档问题 3：0.1.147 声明未对齐时，`pnpm add billion-context@0.1.163` 稳定失败；按上述流程操作后通过。

## 五、原生模块本地 headers 构建（node-gyp nodedir）

**适用场景**：本机到 `https://nodejs.org` 被网络策略拦截（SSL `wrong version number`），`better-sqlite3`、`cpu-features` 等 node-gyp 原生构建下载 headers 失败时。

依据 node-gyp 官方参数（[npmjs — node-gyp](https://www.npmjs.com/package/node-gyp)）：`--nodedir` 指定本地 node headers 目录；经 npm 配置传递即 `npm_config_nodedir`。本机验证可行的完整命令（沿用原记录文档问题 6 的成功方案，实测 16 秒完成）：

```bash
npm_config_nodedir=C:/nodedir npm_config_build_from_source=true \
  PATH="/c/Users/ASUS/AppData/Roaming/npm:$PATH" dsh plugin --profile web add -E <包名>@<版本>
```

- `C:\nodedir` 内需有完整 headers 与 `node.lib`；
- `npm_config_build_from_source=true` 强制源码编译（跳过 prebuild 下载）；
- PATH 前置用于强制 pnpm 12.6.0（规避 12.3.4 的偶发 fail-fast，见原记录文档问题 4）。
