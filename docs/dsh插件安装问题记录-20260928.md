## 三、问题详情

### 问题 1：dsh-db-tool 插件加载失败【高】

**现象**

插件安装成功、版本正确（0.1.8），但启动日志始终出现：

```
dsh: warning: 1 entry did not activate
db-tool (dsh-db-tool): failed to import
```

宿主 0.1.7-rc.1 与升级后的 0.1.7-rc.2 均复现；纯 Node 环境下导入该插件完全正常。

**根因（四层因果）**

1. **宿主缺陷**：dsh 为实现 profile 感知解析，用 `node-addon-require-builtin` 深入 Node 内部模块并改写 CJS 的 `Module._resolveFilename`。每个请求都会经过 `dsh-app-boot/lib/index.js:1422`：

   ```js
   for (const searchPath of createRequire(parent).resolve.paths(name)) {
   ```

   该行**无空值保护**（对比同类调用 `profile.ts:596` 有 `?? []`），在特定请求上抛：

   ```
   TypeError: createRequire.resolve.paths is not a function or its return value is not iterable
       at ResolutionRouter.routeScoped (.../dsh-app-boot/lib/index.js:1422:58)
       at ResolutionRouter.routePath (...:1554)
       at Module.wrappedFilename [as _resolveFilename] (...:1771)
   ```

2. **为何是 mongodb 触发**：dsh 的 `selfReferenceName()` 只在包声明了 `exports` 字段时才短路解析。`mongodb@7.6.0` 是**无 exports 的老式布局**（132 个 js 文件），内部请求全部经过缺陷循环；而 `bson@7.3.3` 有 exports，不触发。纯 Node 下穷举 mongodb（132 文件 × 8 种子路径请求）的 `resolve.paths` 调用：**零异常**，证明包本身无问题。

3. **为何是 db-tool 撞上**：其加载链 `dist/index.js → manager.js → guard/index.js:10 静态导入 ../adapters/mongodb/index.js → 顶层 import 'mongodb'`。即**加载插件必然加载 mongodb**——而 db-tool 的适配器本设计为惰性加载（`adapters/index.js` 中 8 个驱动全是 `() => import(...)`），是 guard 为取两个常量做的静态导入破坏了惰性。

4. **为何看不到线索**：dsh 启动审计把加载异常吞掉，只打印 `failed to import`（源头 `app-boot` 的 `inactiveEntries`）。

**定位方法**：影子入口二分法——在同一 profile 挂 7 个探针入口（分别导入 db-tool 的各子模块），一次实验即锁定：不碰 mongodb 的 `store`/`adapters` 成功，`guard`/`manager`/`http`/`script` 全部失败。

**修复（插件侧绕过，三处最小改动）**

1. 新增 `dist/adapters/mongodb/ops.js`：把 `DANGEROUS_OPS`、`READ_OPS` 两个纯数据集合拆出；
2. `dist/guard/index.js` 改为从 `ops.js` 导入这两个常量；
3. `dist/adapters/mongodb/index.js` 改为从 `ops.js` 转发导出（对外接口不变）。

**固化**：pnpm patch 官方机制 —— `patches/dsh-db-tool@0.1.8.patch`（3454 字节）+ `pnpm-workspace.yaml` 的 `patchedDependencies`，重装后自动应用。

**验证**：纯 Node 导入成功且不再加载 mongodb → 实例启动 11/11 激活 → 生产服务重启后 `GET /dsh-db-tool/api/connections` 返回 **200**（修复前 404，响应体 `{"ok":true,"data":[]}`）。

**遗留**：真正建立 MongoDB 连接时仍会加载 mongodb 包、仍会踩中同一缺陷，**MongoDB 连接功能暂不可用**（其余 6 种数据库正常）。彻底修复需上游给 1422 行加空值保护（建议反馈上游）。

### 问题 2：MCP 配置被 mcp-manager 覆写丢失【高】

**现象**

`cordis.patch.yml` 在 2026-09-28 08:51（dsh web 运行期间）被从约 82 行改写为 49 行：原本 4 条 MCP 挂载只剩 `mcp-cbmem` 一条，`mcp-intellij`（IDEA）、`mcp-laya`、`mcp-mcphub` 三条丢失；且 `mcp-cbmem` 的 `serverName` 被从 `cbmem` 改成 `cbm`。

**根因（读 `@xxxyz/dsh-mcp-manager@2.2.7/lib/index.js` 确认）**

- 该插件按"块"而非"条目"处理：`insertBlockRange()`（678-691 行）一旦在某 `- insert:` 块内匹配到目标 id，返回范围就是**从 `- insert:` 到下一个顶层 `- ` 的整块**；
- `removeEntryAll()`（713-721 行）把整块并入删除集；UI 的"编辑"（1074-1079 行）与"删除"（1160-1163 行）都会先删整块再（或不）追加；
- 因此**同块内的无标记条目会被连带删除**——4 条 MCP 同处一个 insert 块，误操作一次即全丢；
- 给手工条目补 `# dsh-mcp-manager:server:<id>` 标记也**不能免疫**（`markerRanges()` 657-677 行同样按整块计算）。

这与历史记录中的同类事故（`G:\CLI\github-项目安装核查报告.md` 第 507-509 行）完全吻合。

**处置**

1. 恢复：按历史原文补回丢失的 3 条（`mcp-intellij` / `mcp-laya` / `mcp-mcphub`），`dsh --profile web --dump-config` 验证 4 条全部加载；
2. **加固**：把 4 条 MCP 拆成 **4 个独立 `- insert:` 块**，把"误删一条导致全部丢失"降级为"只丢一条"；
3. 备份：`.backup-20260928/cordis.patch.yml.before-mcp-restore`（恢复前）、`cordis.patch.yml.before-split`（拆块前）。

**遗留与建议**

- ⚠️ **不要在 dsh-mcp-manager 的 UI 里"编辑/删除"任何 MCP 条目**（新增/启用/禁用/重启是安全的）；
- `mcp-cbmem` 的 serverName 仍为 `cbm`（工具前缀 `mcp__cbm__*`，原基线 `cbmem`）；恢复时未改回以避免二次风险，如需修回只能手工改文件 + 重启。

### 问题 3：`ERR_PNPM_UNUSED_PATCH` 阻断升级【高】

**现象**：`pnpm add billion-context@0.1.163` 稳定失败：

```
Error: ERR_PNPM_UNUSED_PATCH
  × adding a new package
  ╰─▶ The following patches were not used: billion-context@0.1.147
```

**根因**：`pnpm-workspace.yaml` 的 `patchedDependencies` 声明了 `billion-context@0.1.147: patches/billion-context@0.1.147.patch`。一旦执行升级命令、0.1.147 退出依赖树，该 patch 立即"未被使用"，pnpm 直接拒绝整个操作。**这不是崩溃、不是网络问题，而是版本的确定性阻塞**——换任何 pnpm 版本都会失败。

**处置**：为 0.1.163 重新生成 patch（新版 dist 是压缩格式，旧 patch 上下文无法落位，必须重新生成）→ 复制 patch 文件 → 修改 `pnpm-workspace.yaml` 的 `patchedDependencies` 指向 0.1.163 → **紧接**执行升级 add（切换与升级之间不插入其他 pnpm 命令，最小化不一致窗口）。

**说明**：该 patch 修复的不是安装问题，而是 billion-context 的隧道 DNS 校验：本机内网 DNS 不解析外网域名，导致其内置 deepseek 路由被 403 拒绝。补丁让 DNS 解析失败时对回环客户端放行（非回环仍拒绝，SSRF 防护不变）。

**验证**：patch 文件 sha256 与 lock 记录一致；`node_modules/billion-context/dist/index.js` 中 `ctx.clientLoopback` 出现 3 次（原 2 + 补丁 1）；`catch{` 后紧跟补丁注释与 `if(ctx.clientLoopback)return{ok:true}`。

### 问题 8：诊断探针插件被 dsh 拒绝加载【低】

**现象**：凡是在插件顶层或 `apply()` 内**包装 `Module._resolveFilename` 或 `Module.prototype.require`** 的探针插件，自身都会 `failed to import`；甚至顶层 `import Module from 'node:module'` 也可能触发。普通探针（只做动态 import、读文件）正常。

**解释**：dsh 对模块加载链有自我保护/一致性校验，包装会破坏其内部假设。

**规避**：诊断时改用"影子入口二分法"（只做静态导入、不包装加载器）或"层外探针 + 延迟执行"。

## 四、避坑与操作建议

1. **改插件版本前，先对齐 patch 声明**：`pnpm-workspace.yaml` 的 `patchedDependencies` 必须与实际依赖树匹配，否则一律 `ERR_PNPM_UNUSED_PATCH`。
2. **不要用 dsh-mcp-manager 的 UI 编辑/删除 MCP 条目**（会把整块删掉）；手工编辑 `cordis.patch.yml` 更安全（现已拆成 4 块进一步降低影响面）。
3. **安装/升级前先停 dsh web**（Windows 文件占用会导致 EPERM/EBUSY）；升级后必须重启服务才生效。
4. **统一用 pnpm 12.6.0**：`PATH="/c/Users/Sjc/AppData/Roaming/npm:$PATH" dsh plugin ...`（规避 12.3.4 的偶发 fail-fast）。
5. **构建原生模块时用本地 headers**：`npm_config_nodedir=C:/nodedir npm_config_build_from_source=true`（本机到 nodejs.org 被拦）。
6. **本机 HTTP 探测加 `--noproxy '*'`**（Git Bash 的 http_proxy 会拦截回环请求）。
7. **改配置前先备份**：本次全程滚动快照在 `.dsh\profiles\web\.backup-20260928\`。
8. 兼容性被拒时用官方豁免（`dsh plugin --profile web allow-version <pkg>@<ver> --dsh-version <ver> --accept-risk`），并记录豁免清单。
